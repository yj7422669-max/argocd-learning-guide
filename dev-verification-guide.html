1 · 팀 dev 서버 터미널

내가 테스트할 웹은 어느 버전일까?

이미지 태그는 실행할 앱의 버전표예요. GitHub의 dev 설정에 적힌 태그와 dev Deployment의 이미지 끝에 붙은 태그를 비교해요.

kubectl -n ideaconnection-dev get deployment web -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'

예를 들어 출력이 ghcr.io/…/idcn-web:5e74d5a라면 Deployment에 5e74d5a가 설정돼 있다는 뜻이에요. 이 번호는 당시 예시예요. 오늘 비교할 때는 현재 GitHub 파일을 열어 image.tag를 봐요. 팀 GitHub · 웹 dev 이미지 설정

두 태그가 다르면 어느 버전이 설정돼 있는지 기록하고, 다음 단계에서 web-dev의 동기화 상태를 확인해요.

2 · 팀 dev 서버 터미널

Git에 적힌 배포 설정이 반영됐을까?

kubectl -n argocd get applications.argoproj.io web-dev gateway-dev

web-dev는 웹 배포를, gateway-dev는 Gateway 경로 설정 등을 관리해요. Synced는 비교한 설정이 일치한다는 뜻이고, Healthy는 Argo CD가 해당 리소스 상태를 정상으로 본다는 뜻이에요.

연후님이 직접 본 것은 gateway-dev · Synced / Healthy예요. 이 조회는 터미널에서 할 수 있어요. Argo CD 관리 화면의 인증서 경고는 그 화면으로 연결할 때의 문제예요. 웹 사용 흐름은 4단계에서 확인해요.

3 · 팀 dev 서버 터미널

조직 요청을 처리할 백엔드가 준비됐을까?

kubectl -n argocd get applications.argoproj.io user-service-dev
kubectl -n ideaconnection-dev get deployment user-service

첫 줄은 Argo CD의 배포 상태를 봐요. 두 번째 줄은 실제 서비스의 Deployment에서 READY가 1/1인지 봐요. 1/1은 필요한 복제본 1개가 준비됐다는 뜻이에요.

NotFound면 앱 등록 또는 배포가 됐는지 확인해요. 0/1이면 user-service 담당자와 기동 상태부터 확인해요. 브라우저 로그인과 조직 기능은 다음 단계에서 실제로 눌러 봐요.

4 · 내 PC의 테스트용 Chrome

팀원이 쓰는 주소에서 직접 확인하기

팀 README대로 로컬 WSL에서 SSH 프록시를 켜고, Windows에서 해당 프록시를 쓰는 테스트용 Chrome을 열어요. 연후님 로컬 SSH 별명은 t3-dev-cp였어요. 팀 GitHub · 테스트용 Chrome 실행 방법

ssh -N -D 127.0.0.1:1080 t3-dev-cp

Chrome에서 팀 dev 웹 주소 http://10.10.24.101/를 열어요. 아래 항목은 직접 확인한 것만 체크해요. 체크는 이 화면에서 복습할 때 사용해요.

  1. → Gateway를 거쳐 웹에 도착했어요.
  2. → Keycloak 로그인 흐름을 확인했어요.
  3. → 웹에서 조직 조회와 생성 기능을 확인했어요.
  4. → 다시 조회해도 만든 조직을 확인할 수 있어요.
팀 리뷰에 쓸 API 응답은 어디서 봐요?

Chrome에서 F12 → Network → Fetch/XHR를 열고 새로고침해요. /api/users/me와 /api/orgs 요청을 눌러 Request Method가 GET인지, Status가 200인지 확인해요. 조직 생성 요청은 POST이므로 조회 요청과 구분해서 실제 상태 코드를 기록해요.

웹은 열리는데 조직 목록만 404라면, 실패한 요청 주소와 상태 코드를 기록해요. Gateway의 API 경로와 user-service 쪽에서 요청을 어떻게 받았는지 함께 확인할 단서가 돼요.
